An LLM system has no specification you can execute. The same input can produce different outputs, a correct answer can be worded a thousand ways, and every change (a prompt edit, a model upgrade, a new document in the index) can fix some cases while silently breaking others. **Evals turn "it seems to work" into a measured claim.** They are the test suite, the definition of "good" and the early-warning system of an AI product, and the clearest interview signal of production experience: anyone can call an API; few can say how they know it works and how they would know it stopped working.

## 1. What an eval is, and deciding what to measure

```mermaid
flowchart LR
    D["Dataset:<br/>inputs + expected<br/>outcomes or criteria"] --> T["Target: one exact<br/>configuration<br/>of the system"]
    T --> O["Outputs + intermediate<br/>data: retrieved docs,<br/>tool calls"]
    O --> G["Evaluators:<br/>one per criterion"]
    D --> G
    G --> S["Scores per case,<br/>per criterion,<br/>per slice"]
```

- **Dataset**: the cases. Each is an input plus what the grader needs: a reference answer, facts that must appear, the documents that should be retrieved, or just criteria.
- **Target**: the exact system under test, identified by a **configuration version** (prompt version, model snapshot, retrieval settings, tools, index version). A score without its configuration means nothing.
- **Outputs**: record intermediate artefacts (retrieved chunks, tool calls) as well as the final answer; many graders need them.
- **Evaluators**: functions that score one output on one criterion, `evaluate(inputs, outputs, reference) -> score`.
- **Aggregation**: per criterion and per **slice** (question type, language, customer tier). One run of a dataset against a target is an **experiment**; decisions come from comparing experiments.

The distinctions to name:

- **Offline vs online**: offline evals run a fixed dataset before release ("is this version good enough to ship?"); online evals grade sampled live traffic after release ("is what is running still good?").
- **Reference-based vs reference-free**: the first compares with a known-good answer (correctness); the second judges the output on its own or against its inputs (groundedness, relevance, format). Production traffic has no references, so online evals are reference-free.
- **Capability vs regression**: capability evals hold hard cases the system cannot yet do reliably, with low pass rates you work to raise; regression evals hold what already works and should stay near 100%, so a drop blocks release. A capability case that becomes reliable graduates to the regression suite.
- **Component vs end-to-end**: component evals test one stage (retrieval, a classifier, one tool call); end-to-end evals test the whole request. End-to-end says whether users are served; component evals say what to fix.

**Deciding what to measure: error analysis.** The common mistake is to start from metrics: install a library, compute "helpfulness" and "coherence", report averages. Generic metrics rarely match how **your** system fails, so they move without meaning. **Measure your failures, not someone's list of qualities.**

```mermaid
flowchart LR
    S["Sample about 100<br/>real traces,<br/>varied"] --> OC["Open coding:<br/>a note on the first<br/>thing that went wrong"]
    OC --> AC["Axial coding:<br/>group notes into<br/>failure categories"]
    AC --> CT["Count per category,<br/>rank by frequency<br/>x impact"]
    CT --> EV["Evaluator per category,<br/>fix the biggest"]
    EV -->|"repeat as the<br/>system changes"| S
```

1. **Sample traces**: about 100 complete records (input, intermediate steps, output), varied across types and time. Without traffic, generate realistic inputs and run them.
2. **Open coding**: read each trace and write a short, specific note on the **first** thing that went wrong; later errors are often consequences of the first.
3. **Axial coding**: group the notes into **failure categories** and count them; keep reading until new traces stop producing new categories (**saturation**).
4. **Prioritise** by frequency times impact. The top categories become your first evaluators and often your first fixes: many failures are found and fixed by reading, before any metric exists.

A **domain expert** reads, one person owns the definition of good, judgements are **binary per category**, and the analysis is redone after major changes because failure categories shift.

Say it like this: "An eval is a dataset, a pinned configuration of the system, evaluators that each score one criterion, and results per criterion and slice. I decide what to measure by error analysis: read about a hundred real traces, note the first failure in each, group the notes into categories, and build evaluators for the most frequent and costly ones."

## 2. Datasets and graders

**Where cases come from**, best first:

- **Production traces**, sampled across slices and time, especially failures, complaints and escalations.
- **Failure cases from error analysis**, each kept forever as a regression case.
- **Synthetic cases to fill gaps**: list the dimensions that matter (user type, intent, difficulty, language, edge condition), combine them, and have an LLM write realistic inputs for each combination. Generating from dimensions gives coverage; "generate 50 questions" gives 50 near-duplicates.
- **Adversarial cases** (injections, out-of-scope requests, abusive input) and **unanswerable cases** (the answer is not in the data, to test abstention).

Labels per criterion: reference answers, must-include facts, relevant document ids, expected tool calls, rubrics. Start with 50 to 100 targeted cases and grow to hundreds, with enough cases in every slice you will make decisions on. Version the dataset, deduplicate it, keep eval cases out of prompts and few-shot examples, refresh it from production, and keep a held-out set you never tune on.

"Your golden set is 50 synthetic questions; what can't it tell you?": how real users phrase things, the real mix of question types, messy or multi-turn inputs, and failure modes nobody imagined. Questions generated from a passage reuse its words, so retrieval looks better than it will in production. And at 50 cases, a difference of a few points is noise.

**Graders**

- **Code**: exact match, regex, JSON schema validation, numeric tolerance, running generated code against tests, executing generated SQL and comparing result sets, checking that a required tool was called with the right arguments. Cheap, fast, deterministic: use code wherever the criterion allows.
- **LLM judges**: for semantic or subjective criteria such as groundedness, relevance, tone and policy compliance. Flexible and scalable, but they must be validated (section 3).
- **Humans**: domain experts produce gold labels, calibrate judges and grade high-stakes or ambiguous cases. Slow and expensive; the ground truth everything else is checked against.

**Binary pass/fail beats 1 to 5 scores.** Binary forces a precise definition of good, is easier for people and judges to agree on, and aggregates into an interpretable rate. Scales drift, middle values are ambiguous, and annotators disagree on what a 3 is. If you need nuance, use several binary criteria.

## 3. LLM judges you can trust

**Designing a judge**: one criterion per judge, with a precise definition and examples of a pass and a fail; give it what it needs (question, context, answer, reference); ask for a short critique first and the binary verdict last, in structured output at low temperature; prefer a **different model family** from the generator.

```text
You check whether an answer is supported by the provided context.
PASS: every factual claim in the answer is stated in or directly implied by the context.
FAIL: any claim is missing from the context, contradicts it, or adds specifics
(numbers, names, dates) the context does not contain.
"Not in the documents" answers are PASS when the context lacks the answer.
Return JSON: {"critique": "<which claims are or are not supported>", "verdict": "PASS" | "FAIL"}
<context>...</context> <question>...</question> <answer>...</answer>
```

**Calibrating a judge against people**

1. A domain expert labels 100 to 200 examples, with both passes and fails.
2. Split them into a development set (to improve the judge prompt) and a test set (to measure it once).
3. Measure on the test set: **TPR (true positive rate)**, the fraction of human passes the judge passed, and **TNR (true negative rate)**, the fraction of human fails the judge failed. Judges tend to be lenient, so TNR is usually the weak number, and raw accuracy hides it when most cases pass.
4. **Cohen's kappa** measures agreement beyond chance: `kappa = (po - pe) / (1 - pe)`, where po is the observed agreement and pe the agreement expected by chance. With 40 items, agreement on 34 gives po = 0.85; if the human and the judge each label half as pass, pe = 0.5 x 0.5 + 0.5 x 0.5 = 0.5, so kappa = (0.85 - 0.5) / 0.5 = 0.70: substantial agreement.

**Correcting a measured rate for an imperfect judge**: if the judge reports a pass rate p_obs, the true rate is approximately `(p_obs + TNR - 1) / (TPR + TNR - 1)`. With p_obs = 0.80, TPR = 0.90 and TNR = 0.85: (0.80 + 0.85 - 1) / (0.90 + 0.85 - 1) = 0.65 / 0.75, about 0.87.

**Biases and their fixes**

- **Position bias** (in pairwise comparisons, prefers the first or second answer): run both orders and count only consistent verdicts.
- **Verbosity bias** (prefers longer answers): state that length is not quality; compare at similar lengths.
- **Self-preference** (prefers outputs of its own model family): use a different family.
- **Leniency** (passes what it is shown): measure TNR; include clear fail examples in the prompt.
- **Anchoring on the reference** (fails correct answers worded differently): define equivalence explicitly.
- A grounding check from the **same model family as the generator** shares its blind spots and approves exactly the errors it exists to catch; use another family, or prove its TNR on known-bad examples.

Say it like this: "I trust a judge only after calibrating it against an expert's labels: a dev set to tune the prompt and a test set to report TPR and TNR, because judges are lenient and accuracy hides that, plus Cohen's kappa for agreement beyond chance. I control position, verbosity and self-preference bias, use a different model family from the generator, and correct measured rates for the judge's error rates."

## 4. Evaluating RAG, and reading results honestly

```mermaid
flowchart LR
    Q["Question"] --> RET["Retrieval"]
    RET --> CTX["Context"]
    CTX --> GEN["Generation"]
    GEN --> A["Answer"]
    RET -.- RM["recall@k, MRR, nDCG,<br/>context precision<br/>and recall"]
    GEN -.- GM["faithfulness,<br/>answer relevance"]
    A -.- CM["correctness against<br/>a reference"]
```

Score each stage separately, so a failure points to its stage.

**Retrieval metrics** (need labels saying which chunks are relevant to each question): **recall@k**, the fraction of relevant chunks found in the top k; **precision@k**, the fraction of the top k that is relevant; **MRR**, 1 / rank of the first relevant result, averaged over questions; **nDCG@k**, which rewards relevant results more the higher they rank (each hit discounted by log2(rank + 1)), normalised by the best possible ordering.

Worked example: three relevant chunks sit at ranks 2, 7 and 11. recall@5 = 1/3 = 0.33 and recall@10 = 2/3 = 0.67. MRR = 1/2 = 0.5. nDCG@10 with binary relevance: DCG = 1/log2(3) + 1/log2(8) = 0.631 + 0.333 = 0.964; the ideal order puts the three at ranks 1 to 3, giving 1 + 0.631 + 0.5 = 2.131; nDCG@10 = 0.964 / 2.131 = 0.45.

**Answer metrics**

- **Faithfulness (groundedness)**: the fraction of the answer's claims supported by the retrieved context. Reference-free.
- **Answer relevance**: does the answer address the question? Reference-free.
- **Context precision**: are the relevant chunks ranked at the top of the context? Needs relevance labels or a reference answer (a reference-free variant judges against the generated answer).
- **Context recall**: does the context contain everything the reference answer needs? Needs a reference.
- **Correctness**: does the answer match the reference? Needs a reference.
- **Faithfulness is not correctness.** "Faithfulness is 0.95 but users say the answers are wrong" means the model faithfully repeats the wrong evidence: stale or superseded documents, the wrong section, an incomplete context, or a misunderstood question. Measure context recall and correctness with references, check document versions and freshness, slice by topic, and check that the faithfulness judge is not lenient.

**Reading results without fooling yourself**

- **Noise**: the standard error of a pass rate is `sqrt(p x (1 - p) / n)`. At p = 0.8 with n = 51 it is about 0.056, so the 95% interval is about plus or minus 0.11: a 0.02 difference on 51 questions is noise.
- **Paired comparison**: run both versions on the same questions and look at the **discordant pairs**, questions one passes and the other fails. A bootstrap over questions, or McNemar's test, says whether the difference is real; pairing removes question-difficulty noise.
- **Non-determinism**: run each case several times; report the mean and the spread.
- **Slices**: an average can rise while an important slice regresses, so report and gate per slice.
- **Look at the examples that changed**, not only the numbers; keep a **held-out set** so a prompt tuned on the eval set cannot fool you; use **one primary metric plus guardrail metrics** (quality up while latency, cost and safety stay within limits).

**In the workflow**: every change (prompt, model, retrieval settings, tools) runs the fast regression suite in CI with blocking thresholds per slice against the baseline; the larger suite with judges and capability cases runs nightly or before release; experiments are tracked by configuration version, and outputs are kept so graders can be re-run cheaply; eval cost is controlled by caching outputs, sampling, and screening with cheaper judges first.

## 5. Evaluating agents

Agents are harder to evaluate: many steps, tools with side effects, many valid paths, non-determinism and state.

**Three levels**

- **Outcome**: was the goal achieved? Check the **final state of the environment**, not the agent's claim: the refund exists with the right amount, the tests pass, the record changed correctly.
- **Trajectory**: the path: required tools called, forbidden ones not, arguments correct, order respected where it matters, steps within budget.
- **Single step**: given this exact state, was the next action right? Unit tests for decisions: cheap and precise.

**Trajectory evaluation: exact match is too strict**, because there are many valid orders and harmless extra steps. Check instead: required calls present (subset match), forbidden calls absent, ordering constraints only where they matter (verify before refund), argument correctness, step count within budget, and an LLM judge with a rubric for reasonableness.

**Environments**: sandboxed copies of the tools and data with seeded state (test databases, mock services), reset before every trial, so outcome checks are deterministic. For multi-turn agents, a **simulated user**: an LLM playing a persona with a goal and private information it reveals only when asked; grade the final state of the database and the conversation's policy compliance. Include users who change their minds, give partial information or go off topic, and grade per turn (policy, tool use) and per conversation (goal completed, turns to resolution, recovery from misunderstandings, context carried across turns).

**Reliability: pass@k and pass^k.** With per-trial success probability p:

- **pass@k** = 1 - (1 - p)^k: the chance that **at least one** of k tries succeeds. Fits tasks where a person or a verifier picks the best of several attempts (code generation with tests).
- **pass^k** = p^k: the chance that **all** k tries succeed: consistency. Fits customer-facing agents, where every customer gets one attempt.
- At p = 0.8: pass@3 = 1 - 0.2^3 = 0.992, while pass^3 = 0.8^3 = 0.512. An agent that "works 80% of the time" handles three customers in a row correctly only half the time.

Score agent failures by category: wrong tool, wrong arguments, loops, premature "done", policy violations, ignored tool errors, claimed actions that never happened.

Say it like this: "For a tool-using agent I build a sandboxed environment with seeded state and a simulated user, grade the final state of the environment rather than the agent's claim, check trajectories with required and forbidden calls instead of exact match, and run each task several times to report pass^k, because a customer-facing agent has to be right every time, not once in three tries."

## 6. Production: online evals, drift, shipping safely, and the flywheel

**Online evals.** Every request's trace (inputs, outputs, configuration versions, retrieved ids, tool calls, tokens, latency, feedback) is the raw material. Run reference-free evaluators (groundedness, policy, PII, format) on a sample of live traffic, and track implicit signals: thumbs-down and regenerate rates, escalations to humans, abandonment, users rephrasing the same question, conversation length to resolution, refusal rate, format and validation errors, tool error rate, and latency and cost per resolved task. Explicit feedback is sparse and skewed toward unhappy users, so implicit signals matter more.

**Drift** comes from inputs (new topics, languages, user types), data (the corpus changed) and the model (a provider update behind the same name). "The provider silently updated the model; how do you find out before users do?": pin dated model snapshots where offered; run a scheduled canary eval suite against the live endpoint every day; watch output statistics (length, refusal rate, format errors, judge scores) for shifts; alert and investigate before users report it.

**Shipping safely**

```mermaid
flowchart LR
    OF["Offline evals<br/>pass"] --> SH["Shadow: run on<br/>live traffic,<br/>not shown"]
    SH --> DF["Internal<br/>dogfooding"]
    DF --> CN["Canary: 1 to 5%<br/>of users, auto<br/>rollback"]
    CN --> AB["A/B test on<br/>product metrics"]
    AB --> FULL["Full rollout<br/>behind a flag"]
```

Each rung adds real-world exposure while limiting the damage, and any rung can roll back. For agents that act, ladder the **autonomy** too: suggest-only, then act with approval, then act alone for low-risk actions. "A stakeholder wants to launch, but the eval evidence is weak": state what is measured and how uncertain it is, then offer a bounded launch (a canary or one segment, human review or suggest-only mode, monitoring, a kill switch, agreed success criteria) plus a time-boxed plan to strengthen the evals. Neither block blindly nor launch blindly.

**The flywheel**

```mermaid
flowchart LR
    PR["Production<br/>traces"] --> EA["Error<br/>analysis"]
    EA --> DS["New eval cases<br/>and criteria"]
    DS --> FX["Fixes:<br/>prompt, retrieval,<br/>tools, model"]
    FX --> GT["Evals gate<br/>the release"]
    GT --> MO["Monitor<br/>online"]
    MO --> PR
```

Every production failure becomes an eval case, every fix is proven on the evals, every release is monitored. The dataset grows from reality, which is why mature teams improve quickly.

**How evals fail**: vibes (a few hand-tried prompts instead of a dataset); generic metrics unrelated to the real failures; judges with unknown TPR and TNR; unrepresentative, stale or synthetic-only datasets; overfitting to the eval set and leakage of eval cases into prompts; too few cases for the differences claimed; averages that hide slice regressions; grading only final answers of agents, ignoring trajectories and side effects; ignoring cost and latency in the quality decision; no re-run after model updates; and nobody owning the eval set.

Say it like this: "Offline evals gate every release; online, I run reference-free judges on sampled traffic and watch implicit signals like rephrasing, escalations and regenerations, with a daily canary suite to catch silent model changes. New versions climb a ladder of shadow, canary and A/B tests, and every production failure becomes a new eval case."
