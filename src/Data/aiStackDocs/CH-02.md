Retrieval-augmented generation (RAG) answers questions from your own documents: at question time, find the relevant passages, put them in the prompt, and make the model answer from them with citations. It is two systems: an **indexing pipeline** that prepares documents, and a **query pipeline** that serves a question. Most RAG quality problems are created in the first and noticed in the second.

## 1. What RAG is, and when it is the wrong tool

```mermaid
flowchart TB
    subgraph IDX["Indexing (offline, continuous)"]
        SRC["Sources:<br/>files, wikis, DBs"] --> PAR["Parse,<br/>OCR, clean"]
        PAR --> CH["Chunk +<br/>metadata"]
        CH --> EMB["Embed"]
        EMB --> IX[("Index: vectors,<br/>text, metadata")]
    end
    subgraph QRY["Query (online, per question)"]
        QN["Question"] --> RW["Rewrite /<br/>understand"]
        RW --> RT["Retrieve<br/>top candidates"]
        RT --> RR["Rerank,<br/>keep the best"]
        RR --> PB["Build prompt"]
        PB --> LLM["LLM"]
        LLM --> ANS["Answer +<br/>citations"]
    end
    IX --> RT
```

- **Indexing** turns documents into searchable chunks: parse, split, embed, store with metadata. It runs continuously as documents change.
- **Query** turns a question into a search, keeps the best passages, and asks the model to answer only from them.
- The index is the contract between the two: whatever parsing or chunking lost cannot be recovered at question time.

**Why retrieval rather than the alternatives.** Compared with fine-tuning, an index updates in minutes, answers can cite sources, and permissions can be applied per user at request time. Compared with putting everything into a long context, it scales to corpora far larger than any window, and every token you do not send saves money, time and accuracy.

**When RAG is the wrong tool**

- **Aggregations and analytics** ("how many tickets were escalated last month, by region"): the data is structured, so use SQL or text-to-SQL. Retrieval returns ten passages; it cannot count fifty thousand rows.
- **Exhaustive questions** ("list every contract with an auto-renewal clause"): top-k returns k items, not all. Extract structured fields at ingestion and query them.
- **Whole-document tasks** (summarise this contract, compare two versions): give the whole document, or map over its sections and combine.
- **Small, stable knowledge** (a 20-page policy): put it in the prompt and use prompt caching. Simpler and more accurate.
- **Live data** (order status, stock levels): a tool call.
- **Behaviour or format problems**: prompting or fine-tuning.

Correction: "Million-token context windows killed RAG." Corpora outgrow any window; cost and time to first token scale with input; accuracy falls with length and distractors; permissions must be enforced per user; and an index updates incrementally. Long context changes RAG (bigger chunks, whole sections) rather than replacing it.

Say it like this: "RAG retrieves relevant passages at question time and makes the model answer from them with citations, so knowledge stays fresh, attributable and permission-aware. I don't use it for aggregations, which belong in SQL, for exhaustive listings, for whole-document tasks, or when the knowledge fits in a cached prompt."

## 2. Embeddings: meaning as geometry

An **embedding model** maps a text to a fixed-length vector so that texts with similar meaning land close together.

**How it learns.** It is trained **contrastively** on pairs that belong together: a question and the passage that answers it, a title and its article. For each pair the loss pulls the two vectors together and pushes away the other passages in the same batch (**in-batch negatives**). **Hard negatives**, passages that look relevant but do not answer (the warranty page for a returns question), force the model to learn fine distinctions; without them it learns only topic.

**How it is used.**

- **Bi-encoder**: query and document are embedded **separately**, so every document vector is computed once at indexing time, and a query costs one embedding plus a nearest-neighbour search. The price is that the model never sees query and document together, which is why a reranker comes later.
- **Similarity**: **cosine** (the angle between vectors), **dot product** (equal to cosine when vectors are normalised to length 1), **L2** (straight-line distance; for normalised vectors it ranks the same as cosine). Use what the model was trained with, normalise, and the three agree on ranking.
- **Asymmetric models** expect markers such as `query:` and `passage:`, or separate query and document modes. Forgetting them silently lowers quality.

**What embeddings miss**: exact identifiers (error codes, SKUs, ticket numbers), rare jargon, negation ("not covered"), numbers and dates, and vocabulary the model never saw. That is why keyword search runs alongside them.

**Choosing an embedding model**

1. Shortlist from the MTEB retrieval leaderboard, in your languages.
2. Measure **recall@k on your own queries and documents**: the only number that decides.
3. Check the **maximum input length** (many models silently truncate at 512 tokens), dimensions (storage), latency and price, hosting (API or self-hosted for data residency), and multilingual support.

**Storage and its levers.** Vectors take N x dimensions x bytes: 10 million chunks x 1,024 dimensions x 4 bytes (float32) is about 41 GB before index overhead.

- **Matryoshka embeddings** are trained so the first m dimensions are themselves a good embedding: truncate 1,024 to 256 dimensions for 4 times less storage and faster search at a small quality cost, or search with short vectors and rescore the top results with full ones.
- **Quantisation**: int8 is 4 times smaller; binary (1 bit per dimension) is 32 times smaller, compared with Hamming distance, with the top candidates rescored using full vectors.
- **Changing the embedding model means re-embedding everything**: vectors from different models live in different spaces. Build a new versioned index in parallel, evaluate both, switch an alias, keep the old one for rollback.

**When domain vocabulary defeats the embedding model**, in order: add keyword search (BM25) as a hybrid, which catches exact terms immediately; enrich chunks with titles, section paths and glossary expansions; expand queries with domain synonyms; evaluate stronger or domain-specific models; **fine-tune the embedding model** (generate synthetic queries from your chunks with an LLM, mine hard negatives with the current retriever, train contrastively, measure recall@k on held-out real queries); add a reranker.

Say it like this: "Embedding models are trained contrastively to pull matching query-passage pairs together and push non-matches apart, especially hard negatives, so meaning becomes distance. With normalised vectors cosine, dot product and L2 rank the same. I pick the model by recall@k on our own queries, not the leaderboard, and version the index because changing the model means re-embedding everything."

## 3. Chunking and ingestion: where quality is decided

**Why split documents at all**: embedding models truncate long input; one vector for a 40-page document averages every topic into a blur (**dilution**), so a specific question matches nothing strongly; and the prompt needs passages, not whole documents.

**The trade-off**: small chunks match precisely but lose context (a sentence such as "this does not apply to contractors" separated from the rule it modifies); large chunks keep context but blur the embedding and spend more prompt tokens.

**Strategies**

- **Fixed size by tokens with overlap** (for example 300 to 500 tokens, 10 to 20% overlap): the simple baseline; it cuts mid-sentence and mid-table.
- **Recursive**: split on the largest natural boundary that fits: sections, then paragraphs, then sentences, then words.
- **Structure-aware**: follow the document's own structure: Markdown or HTML headings, layout sections in PDFs, code by function or class, FAQs by question-and-answer pair, tables whole with their header row.
- **Semantic**: split where the meaning shifts (similarity between neighbouring sentences drops). Costlier at indexing, with mixed results; measure before adopting.

Pick size and overlap by evaluation (recall@k and answer quality on your questions), not folklore: answers that live in one paragraph favour small chunks; answers that need a whole procedure favour larger ones.

**Upgrades for chunks that are too small to understand**

- **Parent-child (small-to-big)**: index small chunks for precise matching; on a hit, send the larger parent section, or the neighbouring chunks, to the model.
- **Contextual chunk headers**: prepend "Document title > Section > Subsection" to each chunk before embedding.
- **Contextual retrieval**: an LLM writes 50 to 100 tokens situating each chunk within its whole document, prepended before embedding and keyword indexing. Anthropic measured failed retrievals falling by about half with contextual embeddings plus contextual BM25, and by about two thirds with reranking added. It costs one LLM call per chunk at indexing, made cheap by caching the full document in the prompt.
- **Multi-representation indexing**: index an LLM-written summary, or the questions a chunk answers, and return the original chunk on a hit.

**Every chunk carries metadata**: document id, version, title, section path, page, source URL, timestamps, tenant id, access-control list, language, document type and content hash. Metadata powers filters, citations, freshness and deletes.

**The ingestion pipeline**

```mermaid
flowchart TD
    SRC["Sources"] --> CON["Connectors:<br/>webhooks, change<br/>capture, polling"]
    CON --> HS{"Content hash<br/>changed?"}
    HS -->|"no"| SKIP["Skip"]
    HS -->|"yes"| QU["Queue"]
    QU --> PRS["Parse: layout,<br/>OCR, tables,<br/>images"]
    PRS --> CLN["Clean, dedupe,<br/>strip boilerplate"]
    CLN --> CHK["Chunk, add<br/>metadata, context"]
    CHK --> EMB["Embed in<br/>batches"]
    EMB --> UP["Idempotent upsert<br/>into the index"]
    PRS -->|"repeated failure"| DLQ["Dead-letter queue<br/>for inspection"]
```

- **Connectors** detect changes by webhook, change-data capture or polling by modified time; a **content hash** skips documents that did not really change.
- **The queue** decouples bursty uploads from rate-limited embedding APIs; workers scale out, retry with backoff, and send documents that keep failing to a **dead-letter queue** instead of blocking the pipeline.
- **Parsing is where most quality is lost**:
  - Multi-column PDFs lose reading order; headers and footers repeat on every page.
  - **Scanned PDFs** have no text layer and need OCR; keep page images and OCR confidence, flag low-confidence pages, and expect errors to flow into every later stage.
  - **Tables** flattened to text lose rows and columns: keep each table whole as Markdown or HTML, index a short natural-language summary of it, and send the full table to the model.
  - Charts and images need vision-model descriptions; emails need quoted replies and signatures stripped.
  - Complex layouts justify layout-aware parsers or a vision model. Common choices: open-source parsers such as Unstructured and Docling, cloud document services (AWS Textract, Azure Document Intelligence, Google Document AI), or a vision model reading page images directly.
- **Idempotent upsert**: the chunk id is derived from (document id, version, position), so a retry overwrites instead of duplicating.
- **Lineage**: record which parser version and embedding model produced each chunk, so you can re-process selectively.

Say it like this: "Chunk size is a precision-versus-context trade-off, so I split along the document's structure, keep tables and procedures whole, attach metadata to every chunk, and tune size on recall@k, adding parent-child retrieval or contextual headers when chunks lose context. Ingestion is a queued, idempotent pipeline where parsing quality, especially OCR and tables, decides most of the final answer quality."

## 4. Keeping the index correct: edits, deletes and permissions

```mermaid
flowchart LR
    EV["Change event:<br/>document v2"] --> WR["Write v2 chunks<br/>(not yet active)"]
    WR --> SW["Switch the document's<br/>active version to v2"]
    SW --> DL["Delete v1 chunks"]
    DEL["Delete event"] --> DA["Delete every chunk<br/>with that document id"]
    REC["Nightly reconcile:<br/>source ids vs index ids"] --> DA
```

- **Edits**: re-parse and re-chunk; compare chunk hashes and re-embed only what changed; write the new version's chunks; switch the document's active version in one step; then delete the old chunks. A search during the switch never sees a mix of old and new.
- **Deletes**: remove every chunk by document id within an agreed time (privacy and legal duties). Events get lost, so a periodic **reconciliation** job compares source ids with index ids and removes orphans.
- **Model or chunking changes**: a full re-index into a new versioned index, evaluated against the old one, switched by alias, with the old index kept for rollback.
- **Freshness** is a metric: lag from "source changed" to "searchable", with an alert.

**Permissions: enforce access in retrieval, never in the prompt.** Once a passage is in the context, the model can repeat it; "do not reveal X" is not a control, and injected text can override it.

- Every chunk carries `tenant_id` and the principals allowed to read it (users and groups).
- At query time, resolve the user's identity and groups from the identity provider (cached briefly) and filter the search: tenant matches **and** the chunk's principals overlap the user's.
- The filter must run **inside** the search. Filtering after taking the top results returns too few or zero results for users who can see little.
- **Store groups, not expanded users**: removing someone from a group then needs no chunk updates at all. A document's own permission change becomes a metadata update on its chunks, without re-embedding, within minutes; strict systems also re-check the final results against the source system at query time (**late binding**).
- **Isolation between tenants**: an index per tenant gives the strongest isolation and simple deletion, but many small indexes are costly to operate; a shared index with a tenant filter is efficient but one filter bug leaks data and heavy tenants slow others; partitions or namespaces per tenant inside one cluster are the usual middle ground, with dedicated indexes for the largest tenants.
- **Everything derived from documents inherits their permissions**: caches (keyed by tenant and permission scope), conversation memory, summaries, eval datasets and traces. Log which chunks were shown to which user.

Say it like this: "Permissions are enforced as filters inside the retrieval query, using the tenant and principals stored on every chunk, so the model never sees text the user can't. Groups are stored rather than expanded users so revocation is instant, document permission changes propagate as metadata updates within minutes, and caches, memory and logs are scoped the same way."

## 5. The query path: prompt, citations, abstention, latency and cost

```mermaid
flowchart TD
    U["User question<br/>+ history"] --> SA["Rewrite into a<br/>standalone query"]
    SA --> SR["Vector + keyword<br/>search, filtered by<br/>tenant and ACL"]
    SR --> C50["About 50<br/>candidates"]
    C50 --> RK["Reranker"]
    RK --> TH{"Best score<br/>above threshold?"}
    TH -->|"no"| NF["Answer: not found<br/>in the documents"]
    TH -->|"yes"| TOP["Top 5 to 8 that<br/>fit the token budget"]
    TOP --> PR["Prompt: rules,<br/>sources with ids,<br/>question last"]
    PR --> GEN["LLM, streamed"]
    GEN --> CV["Validate citations"]
```

- **Rewrite**: a follow-up such as "and for contractors?" becomes "parental leave policy for contractors" before searching.
- **Search** runs with access filters inside the search and returns a generous candidate set.
- **Rerank** scores the candidates precisely; if even the best is weak, answering "not found" is cheaper and more honest than generating.
- **Select** the top passages that fit the budget, never cutting a passage mid-way.
- **Validate** citations after generation.

**Building the prompt**

```text
Answer the question using only the sources below.
- After each claim, cite the source id in brackets, like [S2].
- If the sources do not contain the answer, say you could not find it in the documents.
- Quote numbers exactly. If sources conflict, prefer the most recent and mention the conflict.
<source id="S1" title="Leave policy" updated="2025-03-01"> ... </source>
<source id="S2" title="Contractor handbook" updated="2024-11-12"> ... </source>
Question: Do contractors get parental leave?
```

Most relevant passages first, near-duplicates removed, more than one document represented when possible, and the question last.

**Citations you can trust**: every passage has a short id and the model cites ids per sentence; every cited id must be one you supplied (a fabricated id means dropping the sentence or regenerating); a judge or entailment model checks, on all or a sample of answers, that each cited source supports its sentence; and the user sees the quoted span with a link to the exact page.

**Abstention** has two layers, a retrieval threshold (no good evidence, no generation) and a generation rule with an example, both measured with unanswerable questions in the eval set.

**Latency and cost of one request**

- Query rewrite with a small model (optional): 200 to 400 ms.
- Query embedding: 10 to 50 ms. Vector and keyword search: 10 to 100 ms. Reranking 50 candidates: 50 to 200 ms.
- LLM time to first token: 0.3 to 2 s, growing with the passages sent. Generation: output tokens x 10 to 30 ms.

The LLM dominates; retrieval is rarely the bottleneck. The levers: stream the answer; send fewer, better passages (a reranker lets you send 5 instead of 20, cutting both cost and distraction); cap answer length; cache at every layer (query embeddings, retrieval results, the static prompt prefix, full answers to repeated questions), with every cache keyed by tenant and permission scope and invalidated when its documents change; skip the rewrite on first turns and run independent steps in parallel.

Cost per request is roughly (rules + passages + question tokens) x input price + answer tokens x output price; embedding and reranking are small. **Passages dominate the input**, so retrieval precision directly controls cost.
