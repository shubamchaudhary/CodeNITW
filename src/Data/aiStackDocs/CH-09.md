## 1. Grade what happened, not what the agent says

An agent's final message is a claim. The truth lives in the **system of record**: the database or service that actually holds the data. Testing an agent happens at three levels:

- **Final outcome**: did the task really succeed? After "refund order 48213, it arrived broken", does the payments system hold exactly one $40 refund on order 48213, and none on any other order?
- **Trajectory**: the sequence of tool calls the agent made, checked against rules. Did it read the order before refunding? Did it request approval before any refund over the limit? Did it never call a delete tool? Did it finish within 12 steps? Rarely demand an exact sequence: there are usually several valid paths, and rigid matching punishes good runs.
- **Single step**: given this exact state, is the next tool call the right one? Useful for finding *where* a run goes wrong.

```mermaid
flowchart LR
    TASK["Test task:<br/>refund broken<br/>order 48213"] --> ENV["Fresh sandbox:<br/>seeded test DB,<br/>fake services"]
    ENV --> RUN["Agent runs<br/>3 times"]
    RUN --> OUT["Outcome check:<br/>one $40 refund on<br/>48213, none elsewhere"]
    RUN --> TRJ["Trajectory rules:<br/>read before write,<br/>approval requested,<br/>at most 12 steps"]
    OUT --> SC["Passed only if<br/>all 3 runs pass"]
    TRJ --> SC
```

Every run starts in a fresh **sandbox**: a test database seeded with known data, and fake versions of external services, so runs cannot interfere with each other or with real systems.

> **Pause and think.** The refund agent passes a task 8 times out of 10. Is that good? Think about the customers: each one sends a request once, and thousands arrive every day.

## 2. One success is not reliability: pass^k

Run the same task k times:

- **pass@k**: the chance that *at least one* of k attempts succeeds. Fits tools where a person picks the best of several attempts, such as code suggestions.
- **pass^k** (read "pass to the power k"): the chance that *all* k attempts succeed, roughly the single-attempt rate raised to the power k. Fits anything facing customers or changing data, because each real request gets exactly one attempt.

```mermaid
xychart-beta
    title "pass^k falls fast: top line 90% per attempt, bottom line 80%"
    x-axis "number of attempts k" [1, 2, 3, 4, 5, 6, 8, 10]
    y-axis "chance all k succeed" 0 --> 1
    line [0.9, 0.81, 0.73, 0.66, 0.59, 0.53, 0.43, 0.35]
    line [0.8, 0.64, 0.51, 0.41, 0.33, 0.26, 0.17, 0.11]
```

At 80% per attempt, pass^3 = 0.8 x 0.8 x 0.8 = 0.51: an agent that "works 80% of the time" handles three customers' requests in a row correctly only about half the time. That is the argument for working on consistency, not just capability. (pass^k comes from tau-bench, a benchmark of customer-service agents talking to simulated users.)

**Testing conversations**: for agents that hold multi-turn conversations, a **simulated user** stands in for a person: a model plays the customer from a scenario card (their goal, the facts they know, when they give up) and chats with the agent until the task is done or a turn limit is reached. Then grade the outcome and the conversation. Read a sample of transcripts by hand; an unrealistic simulated user produces misleading scores.

**Measuring where it goes wrong**: tool selection accuracy (right tool on steps with a known right tool), argument accuracy (right order id, right amount), steps and cost per successful task, and recovery rate (after a tool error, did it recover or give up?). When reviewing failed runs, the same categories recur; tag them like chapter 8's failure categories:

```mermaid
flowchart TB
    F["Failed agent run"] --> A["Wrong tool or<br/>wrong arguments"]
    F --> B["Looped or stalled"]
    F --> C["Claimed success<br/>without checking"]
    F --> D["Forgot an earlier<br/>constraint"]

```

Weekly counts tell you whether to fix tool descriptions, loop limits, verification steps, memory, or guardrails.

You will hear about public agent benchmarks: SWE-bench (fixing real code issues), tau-bench, GAIA. They help compare models in general and say little about your store's orders and refunds. Use them as a shortlist; decide with your own tasks.

## 3. See every request: traces and observability

**Observability** means being able to answer "what happened in this request, and why?" after the fact. Its core is the trace: one record per request with a nested entry for every model call, search and tool call. Tools such as LangSmith and Langfuse store and display them; OpenTelemetry has standard conventions for them.

What each trace must hold:

- the model and its exact version, and the prompt template version;
- the input messages (personal data masked);
- retrieved chunk ids and scores; tool calls with arguments, results and errors;
- the answer, tokens in and out, time to first word and total time, cost;
- who asked (customer or support rep, workspace, conversation id), and the thumbs up or down that arrives later.

Decide retention and masking rules up front: traces often contain sensitive data.

## 4. Grade live traffic: online evals

**Online evals** run checks on a sample of real production traces, continuously. They must work without a known-good answer, since live questions have none: code checks (citations valid, format right) and calibrated judges (grounded or not). Chart the results **per group** (customer plan, region, question type) and alert on drops: an average across everything hides a regression in one area.

Signals worth watching alongside them: thumbs-down rate; how often an answer is regenerated or the same question asked again in other words; escalations; format failures; refusals; answer length; time and cost per request.

**Decision point: the provider silently updated the model. How do you catch it before your users do?**

- **Pin dated model versions**, so updates happen when you choose.
- **Run the regression suite daily** against the live model.
- **Watch the signals that move instantly** when a model changes: answer length, refusal rate, format failures, token counts. Tuesday's longer answers and new refusals were exactly that.
- **Keep the previous version one configuration switch away.**

Make feedback easy and useful: one click on every answer, an optional reason from a short list ("wrong", "outdated", "too long", "did not answer"), implicit signals (copying is good, rephrasing is bad), and a weekly review in which real failures go into the golden set. Feedback that only feeds a dashboard teaches nothing.

## 5. Ship in steps

```mermaid
flowchart LR
    OF["Offline:<br/>golden set passes"] --> SH["Shadow: new version<br/>runs on real traffic,<br/>output hidden"]
    SH --> CA["Canary: 5% of<br/>users"]
    CA --> FU["Full rollout"]
    CA -->|"thumbs-down or<br/>escalations up"| RB["Roll back by<br/>configuration"]
    FU --> ON["Online evals,<br/>alerts per group"]
    ON -->|"new failures"| GS["Into the<br/>golden set"]
```

- **Offline**: the golden set must pass before anything ships.
- **Shadow**: the new version answers real questions in parallel, but users still see the old answers; you compare without risk.
- **Canary**: a small group gets the new version. The success metric (resolved without escalation) and the **rollback triggers** (thumbs-down rate, escalations) are written down *before* it starts.
- **Full rollout**, then online evals; every new failure becomes a golden-set case.
- Rolling back is a configuration change, not a redeploy, so it takes seconds.

**A/B tests** answer a different question: not "does it break?" but "is it better?". Split users randomly into two groups, old version and new, and compare a metric chosen in advance:

```mermaid
flowchart LR
    U["Users"] --> SPL["Random split<br/>by user id"]
    SPL --> A["Group A:<br/>current prompt"]
    SPL --> B["Group B:<br/>new prompt"]
    A --> M["Compare: resolved<br/>without escalation,<br/>complaints, cost"]
    B --> M
    M --> D["Decide when the<br/>planned sample size<br/>is reached"]
```

Split by person, not by request, so each user sees one consistent version; pick one primary metric plus guardrail metrics that must not get worse; fix the sample size in advance (stopping as soon as it looks good produces false wins); and run long enough to see past novelty.

**Version everything together.** A change in behaviour can come from the prompt, the model, the search settings, the tools or the index. Record them as one **configuration version** on every trace (for example `refund-agent@2026-11-03.2`: prompt v14, model snapshot, reranker on, index v7). Then every score, experiment and incident maps to an exact configuration, and rolling back means switching to an earlier one.

Also asked: "A stakeholder wants to launch, but the evidence is weak." Do not just say no. State what the evals do and do not show, propose a shadow run or a small canary with a written success metric and rollback trigger, review a daily sample by hand, and set a date to decide from the data.

## 6. Complete example: pass^k and trajectory rules

```python
def pass_hat_k(results_by_task):
    # results_by_task: {task_id: [True, True, False, ...]} from k runs each
    return sum(all(runs) for runs in results_by_task.values()) / len(results_by_task)

def check_trajectory(calls, max_steps=12):
    names = [c["name"] for c in calls]
    problems = []
    if len(calls) > max_steps:
        problems.append("too many steps")
    if "issue_refund" in names and "get_order" not in names[: names.index("issue_refund")]:
        problems.append("refunded without reading the order")
    if "issue_refund" in names and "request_approval" not in names[: names.index("issue_refund")]:
        problems.append("refunded without approval")
    if "delete_order" in names:
        problems.append("called a forbidden tool")
    return problems
```

Expected behaviour:

- `pass_hat_k({"t1": [True, True, True], "t2": [True, False, True]})` returns 0.5: task t2 is not reliable, even though it passed 2 of 3 times.
- A trajectory `get_order, search_policy, request_approval, issue_refund` returns no problems.
- A trajectory that calls `issue_refund` before `request_approval` returns `["refunded without approval"]`, even if the payments system ended up correct, because the path broke a safety rule.
