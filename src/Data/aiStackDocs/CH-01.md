Every GenAI system is built around one component with unusual properties: it is stateless, probabilistic, frozen in time, fluent when wrong, fed through a single text channel, and priced and timed per token. Every later decision (retrieval, agents, evals, caching, guardrails) answers one of those properties. Know the mechanism and you can derive the design instead of memorising it.

## 1. What an LLM is, how it is trained, and why it behaves the way it does

An LLM is a function: given a sequence of tokens, it returns a probability for every token in its vocabulary being next. Generation is that function run in a loop.

```mermaid
flowchart TB
    P["Prompt text"] --> TK["Tokenizer:<br/>text to token ids"]
    TK --> M["Transformer<br/>forward pass"]
    M --> L["Logits: one score<br/>per vocabulary token"]
    L --> S["Sampling:<br/>temperature, top-p"]
    S --> N["Next token"]
    N -->|"append and run again,<br/>until a stop token<br/>or max_tokens"| M
    N --> D["Detokenizer:<br/>tokens to text"]
```

- The tokenizer turns text into integer ids; the model never sees characters.
- One forward pass scores every possible next token; sampling picks one.
- The chosen token is appended and the model runs again, until an end-of-sequence token, a stop sequence or the `max_tokens` cap.

**How it is trained**

```mermaid
flowchart LR
    PT["Pretraining<br/>next-token prediction<br/>on trillions of tokens"] --> SFT["Supervised fine-tuning<br/>prompt and ideal<br/>response pairs"]
    SFT --> PREF["Preference tuning<br/>RLHF or DPO<br/>on ranked answers"]
    PREF --> RL["RL with verifiable<br/>rewards: math, code,<br/>checked by programs"]
    RL --> CHAT["Deployed<br/>assistant model"]
```

- **Pretraining** predicts the next token over web text, books and code; the label is simply the next token (self-supervised). The result is a **base model** that knows language, facts and patterns but only continues text.
- **Supervised fine-tuning (SFT)** trains on (instruction, ideal response) pairs: the model learns to follow instructions, the chat format and the tool-call format.
- **Preference tuning** uses comparisons of two answers. **RLHF** trains a reward model on human preferences, then optimises the model with reinforcement learning (PPO) while a KL penalty keeps it close to the SFT model. **DPO** skips the reward model and the RL loop and directly raises the probability of preferred answers over rejected ones. This shapes helpfulness, tone and refusals, with side effects: **sycophancy** (agreeing with the user) and verbosity.
- **Reinforcement learning with verifiable rewards** rewards answers a program can check (a correct math result, passing tests). Long, self-checking chains of reasoning emerge: **reasoning models**.

**The six properties, and what each forces you to build**

1. **Stateless.** Nothing is remembered between calls; a conversation is the client re-sending the whole history every turn. Memory, sessions and personalisation are your job, and cost grows with conversation length.
2. **Probabilistic.** Output is sampled, so the same input can produce different outputs. You need validation, retries and evals over many runs.
3. **Frozen knowledge.** The model knows its training data up to a cutoff and has never seen your private data. Fresh or private knowledge must arrive through the context: retrieval and tools.
4. **Plausibility, not truth.** It is trained to produce likely text, so it is equally fluent when wrong. And because benchmarks that score only accuracy give a guess some chance of credit and "I don't know" none, models learn to guess. You need grounding, citations, verification, and evals that reward abstention.
5. **One channel.** Instructions, documents, tool results and user text all arrive as tokens in one window; the model cannot reliably tell instructions from data. Prompt injection is structural, not a bug to patch.
6. **Per-token cost and time.** Input tokens cost money and processing time; output tokens cost more and are generated one at a time. Cost and latency are token budgets.

A useful consequence of the training stages: **knowledge comes mostly from pretraining, behaviour from post-training**. That is why fine-tuning changes format and style well but adds facts poorly.

Say it like this: "An LLM predicts the next token in a loop. It's stateless, probabilistic, frozen at a cutoff, optimised for plausibility rather than truth, takes everything through one text channel, and is billed and timed per token. Memory, retrieval, validation, evals, injection defences and token budgets all exist because of those six properties."

## 2. Tokens and the transformer

**Tokens**

- A **tokenizer** (byte-pair encoding) splits text into subword pieces from a fixed vocabulary of roughly 100,000 to 200,000 entries, learned from frequent byte sequences. Common words are one token; rare words, names, long numbers, code and non-English text take several.
- For English, **1 token is about 4 characters or 0.75 words**. JSON, code and many Indian languages use noticeably more tokens per word.
- Each model family has its own tokenizer, so the same text has different token counts across providers.
- Consequences: cost, rate limits and the context window are all in tokens (the window holds input plus output); character-level tasks (counting letters, reversing strings, exact digit arithmetic) are hard because the model sees chunks; verbose formats such as JSON with long keys are expensive; and rare identifiers split into many tokens, so copying an order id exactly is error-prone. Validate ids against your systems.

**Inside the transformer**

Terms first: an **embedding** is a vector (a list of numbers, for example 4,096 of them) representing a token. A **layer** (block) transforms every token's vector. **Attention** lets a token's vector take in information from other tokens. The **MLP** (feed-forward network) transforms each token's vector on its own.

```mermaid
flowchart TB
    T["Token ids"] --> E["Embedding lookup:<br/>one vector per token"]
    E --> B1["Block 1:<br/>self-attention + MLP,<br/>residual connections"]
    B1 --> BN["Blocks 2 to N<br/>(dozens of layers),<br/>same structure"]
    BN --> F["Final vector at<br/>the last position"]
    F --> U["Unembedding:<br/>one logit per<br/>vocabulary token"]
```

- **Embedding lookup**: each token id indexes a learned table and becomes a vector.
- **Blocks**: self-attention mixes information across positions, then the MLP transforms each position (much of the stored knowledge lives in these MLP weights). Each sub-layer adds its result back to its input (a **residual connection**), so information flows through dozens of layers without being lost; normalisation keeps values stable.
- **Position**: attention alone ignores word order; modern models encode position by rotating queries and keys inside attention (**RoPE**).
- **Output**: the last position's final vector is multiplied by the unembedding matrix to give one score (**logit**) per vocabulary token.

**Attention, step by step**

```mermaid
flowchart LR
    X["Token vector"] --> Q["Query:<br/>what am I<br/>looking for"]
    X --> K["Key:<br/>what do I<br/>contain"]
    X --> V["Value:<br/>what I pass on"]
    Q --> SC["Score against the key<br/>of every earlier token,<br/>divided by sqrt(d)"]
    K --> SC
    SC --> SM["Softmax:<br/>weights that<br/>sum to 1"]
    SM --> O["Output: weighted<br/>sum of values"]
    V --> O
```

- Each token's vector is multiplied by three learned matrices to produce a **query**, a **key** and a **value**.
- The query is compared (dot product) with the key of every token **at or before** its position. The **causal mask** forbids looking at later tokens, which do not exist yet at generation time. Scores are divided by the square root of the vector size so softmax does not saturate.
- Softmax turns the scores into weights summing to 1; the output is the weighted sum of the values. The token absorbs information mostly from the tokens it scored highest.
- **Multi-head attention** runs many such heads in parallel with different matrices; heads specialise (grammar, which noun "it" refers to, copying), and their outputs are combined.
- **Grouped-query attention** lets several query heads share one key-value head, which shrinks the memory needed to cache keys and values during generation.
- **Cost**: every token attends to every earlier token, so processing a prompt of n tokens costs on the order of n^2 attention operations, and the cached keys and values grow linearly with n.

Say it like this: "Each token produces a query, a key and a value. Its query is compared with the keys of all earlier tokens, softmax turns the scores into weights, and the token's new representation is the weighted sum of their values. Many heads do this in parallel, so the model learns different relationships, and the causal mask stops a token from seeing the future."

**Model families you will be asked about**

- **Decoder-only** (GPT, Claude, Llama, Gemini, Qwen): causal attention, generates text. Every chat LLM.
- **Encoder-only** (BERT family): every token attends to every other in both directions; strong representations, no generation. Used for classifiers, entity extraction, **cross-encoder rerankers** and classic embedding models (many modern embedding models are adapted decoder LLMs instead).
- **Encoder-decoder** (T5, the original transformer): an encoder reads the input, a decoder generates; translation and summarisation, rare for chat today.
- **Mixture of experts (MoE)**: the MLP in each block is replaced by many expert MLPs and a **router** that sends each token to its top few experts. Total parameters are large, active parameters per token small (Mixtral 8x7B: about 47B in total, about 13B used per token): big-model quality at closer to small-model compute, though all experts must still fit in GPU memory.
- **Multimodal**: an image is cut into patches, encoded by a vision encoder and projected into vectors the language model reads like tokens. Cost scales with resolution (hundreds to thousands of tokens per image). Weak spots: tiny text, exact counts, precise positions; images can carry hidden instructions.

## 3. Inference: prefill, decode, the KV cache and sampling

```mermaid
flowchart TB
    PR["Prompt:<br/>all input tokens"] --> PF["Prefill: one parallel<br/>pass over the prompt,<br/>compute-bound"]
    PF --> KV["KV cache: keys and<br/>values of every token,<br/>per layer, in GPU memory"]
    PF --> T1["First output token<br/>(time to first token)"]
    T1 --> DC["Decode: one pass<br/>per new token,<br/>memory-bound"]
    KV --> DC
    DC -->|"each new token's keys<br/>and values are added"| KV
    DC --> TN["Tokens 2, 3, ...<br/>(time per output token)"]
```

- **Prefill** pushes all prompt tokens through the model in one parallel pass. It is limited by GPU compute and grows with prompt length, and it produces the KV cache and the first output token. **Time to first token (TTFT)** is queueing plus prefill.
- **The KV cache** holds the keys and values of every token so far, for every layer, in GPU memory. Each decode step computes the query, key and value for the **new token only** and attends to the cached ones, instead of reprocessing the whole sequence.
- **Decode** produces one token per forward pass. Each pass must read all model weights and the KV cache from GPU memory, so it is limited by memory bandwidth, not compute. **Time per output token (TPOT)** is roughly constant for a given model, hardware and load.
- **Total latency is about TTFT + output tokens x TPOT.** With a 0.5 s TTFT, 500 output tokens at 20 ms each add 10 s: output length usually dominates.

Consequences:

- **Shorter outputs are the biggest latency lever**, and streaming hides the rest: the user starts reading after TTFT.
- **Output tokens cost more than input tokens** (often 3 to 5 times), because each needs its own sequential pass while input is processed in parallel.
- **Prompt caching**: the provider keeps the KV cache of a prompt prefix; a later request with a **byte-identical prefix** skips prefill for it, so it is faster and the cached tokens are billed at a fraction of the normal price. Put stable content first (system prompt, tool definitions, reference documents) and variable content last (history, the question); changing anything early invalidates everything after it.

Say it like this: "Prefill processes the whole prompt in parallel and sets time to first token; decode generates one token per pass, reusing the KV cache, and is bound by memory bandwidth. A longer prompt raises prefill time and input cost, a longer answer adds a fixed time per token, and prompt caching skips prefill for a repeated prefix."

**Sampling**

```mermaid
flowchart LR
    LG["Logits"] --> TP["Divide by<br/>temperature"]
    TP --> TK["Top-k: keep the<br/>k most likely"]
    TK --> NP["Top-p: keep the smallest<br/>set summing to p"]
    NP --> SM["Softmax and<br/>renormalise"]
    SM --> PK["Sample one token"]
```

- **Temperature** divides the logits before softmax. With three candidate logits of 2, 1 and 0, temperature 1 gives probabilities of about 0.67, 0.24 and 0.09; temperature 0.5 doubles the gaps (4, 2, 0) and gives about 0.87, 0.12 and 0.02. Below 1 sharpens, above 1 flattens, near 0 is **greedy decoding** (always the top token).
- **Top-k** keeps only the k most likely tokens. **Top-p (nucleus)** keeps the smallest set whose probabilities sum to p: few candidates when the model is confident, many when it is unsure.
- Low temperature for extraction, classification, code and SQL; higher for brainstorming and varied wording. Tune temperature or top-p, not both.
- Other controls: **`max_tokens`** caps the output, and when it is hit the finish reason is `length` and the text (or JSON) stops mid-way, so always check the finish reason; **stop sequences**; **frequency and presence penalties** against repetition; **logprobs**, the token probabilities, useful as a confidence signal and for routing low-confidence cases; **seed**, best effort only.

**Why temperature 0 is still not deterministic**: floating-point addition is not associative (adding the same numbers in a different order gives slightly different results); GPU kernels change their order of operations with **batch size**, and the batch size depends on how many other users' requests share the GPU at that moment, so servers are not **batch-invariant**; a tiny difference flips a near-tie between two tokens, and every later token diverges. Providers may also update the model behind the same name. Design for it: validate outputs, evaluate over several runs, pin model snapshots, cache responses when identical answers are required.

Correction: "Temperature 0 makes the output deterministic." It makes the choice greedy; the numbers feeding that choice still vary between runs.

## 4. Why models fail: hallucination and the limits of the context window

A **hallucination** is fluent output not supported by facts or by the provided context.

- **Factuality errors**: wrong facts about the world (rare facts, events after the cutoff).
- **Faithfulness errors**: the answer contradicts or goes beyond the provided documents.
- **Fabrication**: invented citations, ids, URLs, API methods, quotes.

Causes, and the mitigation each one calls for:

- **The objective** rewards plausible continuations; nothing inside checks facts. Mitigation: **ground** the answer in retrieved evidence, use tools for live data, code or a calculator for arithmetic.
- **Rewarded guessing**: accuracy-only scoring taught the model that a guess beats abstaining. Mitigation: **allow abstention** explicitly, with an example of answering "not in the sources", and score correct abstention as a pass in your evals.
- **Missing knowledge** (long-tail facts, anything after the cutoff, anything private). Mitigation: retrieval and tools; never ask the model what only your database knows.
- **Prompt pressure**: no allowed "I don't know", leading questions, sycophancy. Mitigation: neutral phrasing and an explicit escape hatch.
- **Context problems**: the answer is absent, buried mid-context, or contradicted by another document. Mitigation: fewer, better passages with dates and ids.
- **Compounding**: each token conditions the next, so an early wrong token is followed by a confident justification. Mitigation: **constrain** outputs (structured output, enums, citations limited to supplied ids, ids checked against the database) and **verify** after generation (each citation exists and supports its sentence; numbers recomputed; several samples compared, with disagreement treated as low confidence: **self-consistency**).
- Lower temperature for factual tasks; human review where an error is expensive; groundedness measured on live traffic.

Correction: "RAG eliminates hallucination." Retrieval fills knowledge gaps; the model can still ignore, misread or embellish the context, so you still verify.

Say it like this: "Models hallucinate because they're trained to produce plausible text and rewarded for guessing, and they fill gaps fluently. I ground answers in retrieved evidence, explicitly allow 'not found', constrain outputs and citations to known ids, and verify claims after generation, with groundedness measured on live traffic."

**The context window: a hard limit and soft limits**

- The window holds everything in one call: system prompt, tool definitions, history, retrieved content, the user message and the output being generated.
- **Hard limit**: exceed it and the API rejects the request, or a framework silently truncates, which is worse because it may drop your instructions or the user's latest message. Count tokens before every call.
- **Soft limits** arrive long before the hard one:
  - **Lost in the middle**: information in the middle of a long context is used less reliably than information at the start or the end.
  - **Context rot**: accuracy falls as the input grows, even on simple lookups, and passages that look relevant but are wrong (distractors) hurt most.
  - Cost and TTFT grow with every input token.
- Rules: send only what is relevant; put the most important material at the start or end (for long documents, documents first and the question last); give every document an id and date so the model can cite and tell versions apart; summarise or trim long histories before they reach the limit.

Correction: "Million-token windows make retrieval obsolete." They allow larger chunks and whole-document reading, but cost, latency, distraction, permissions and freshness still favour sending only what is relevant.

## 5. Steering the model: prompts, structured output and reasoning models

**A production prompt has a fixed anatomy**

1. **Role and goal**: what the model is, what a good result is, who reads it.
2. **Context and data**, clearly delimited (for example `<document id="7">...</document>`), long material first.
3. **Instructions**: steps, constraints, and what to do when information is missing or the request is out of scope.
4. **Output format**: a schema or an exact template.
5. **Examples** (few-shot), including an edge case and an "abstain" case.
6. **The input or question last.**

Principles:

- **Explicit beats clever.** State exactly what you want and the reason behind each rule; models generalise from reasons.
- Say what to do, not only what to avoid.
- **Delimit untrusted text**; never splice user or document text into the instructions.
- **Few-shot examples teach surface features.** Use three to five diverse examples with a consistent format. Models over-predict the label most common among the examples and favour the label of the last one, so balance and shuffle them; when inputs vary widely, retrieve the examples most similar to the current input (dynamic few-shot).
- **Chain of thought** (reasoning before the answer) improves multi-step math, logic and planning on non-reasoning models, at the cost of output tokens and latency; it adds little for simple lookups and classification, and the written reasoning is not a faithful record of how the model decided. With reasoning models, give the goal and constraints and set the reasoning effort instead of scripting the steps.
- **Decompose.** A chain of small prompts (classify, then extract, then write) is easier to test and fix than one giant prompt.
- **System prompts are not secret.** Users can extract them; never put credentials or private logic there.
- **Prompts are code.** Keep them in version control and log the prompt version with every request; change them only against an eval set built from real failures, compared per slice with the current version; turn every fixed failure into a permanent regression case. That process is the answer when "every fix breaks something else".

**Structured output**

Code needs fields, not prose. Four levels of reliability:

1. **Prompt only** ("reply in JSON"): fails on edge cases with extra prose, comments, or JSON cut off at `max_tokens`.
2. **JSON mode**: guarantees syntactically valid JSON, not your schema.
3. **Schema-constrained decoding** (structured outputs, strict tool calling): at every step the server masks out any token that would break the JSON schema, so the output always parses and matches the schema.
4. **Validate the values anyway**: a valid shape can hold wrong values.

```mermaid
flowchart TD
    RQ["Request with<br/>JSON schema"] --> CD["Constrained decoding:<br/>only schema-valid<br/>tokens allowed"]
    CD --> FR{"Finish reason<br/>normal?"}
    FR -->|"length or refusal"| ESC["Handle: retry with<br/>more tokens, or fall back"]
    FR -->|"yes"| SV{"Values valid?<br/>ranges, ids exist,<br/>dates consistent"}
    SV -->|"yes"| OK["Use the object"]
    SV -->|"no"| RP["Retry once with the<br/>validation error<br/>in the prompt"]
    RP --> SV
    RP -->|"still invalid"| ESC
```

- Check the finish reason first: a refusal or a `max_tokens` stop gives no usable object.
- Validate meaning in code (Pydantic models plus business checks); on failure, retry once with the exact validation error in the prompt (a **repair loop**), then fall back or send to a person.
- **Field order matters**: the model writes left to right, so a `reasoning` field must come before the `answer` field if the answer should use it.
- Use enums for categories, required fields, and **nullable fields for "not found"**, so the model is never forced to invent a value. Keep schemas flat and small; deep optional nesting raises error rates and latency.
- Tool calling is structured output: a tool's arguments are a schema-constrained object.

**Reasoning models**

- Trained with reinforcement learning to produce a long chain of reasoning ("thinking tokens") before answering: they plan, try approaches, check intermediate results and backtrack.
- Spending more computation at answer time (**test-time compute**) buys accuracy on problems whose steps can be checked: math, code, logic, planning, rule-heavy extraction.
- Thinking tokens are billed as output and add seconds to minutes, with highly variable latency; control them with a reasoning-effort setting or a thinking-token budget.
- Use them for hard multi-step tasks, agent planning, complex extraction rules and code; avoid them for simple classification, extraction, routing, and latency-critical or high-volume paths.
- Other ways to spend test-time compute: **self-consistency** (sample several answers, take the majority), **best-of-N with a verifier**, and generate-critique-revise loops.

## 6. Choosing and customising a model

**Choosing a model**, by what actually decides, in order:

1. **Quality on your eval set**: your tasks, your data. Public leaderboards only shortlist.
2. **Latency**: TTFT and output tokens per second at your real prompt sizes.
3. **Cost**: input and output prices, cached-input and batch discounts, and the tokens your prompts use with that model's tokenizer.
4. **Capabilities**: context length, tool-calling reliability, structured output, vision, reasoning modes.
5. **Operations**: rate limits, regions and residency, data-retention terms, SLAs, deprecation schedule.
6. **Open weights or API**: open weights give control, fine-tuning, on-premises deployment and predictable cost at steady high volume, at the price of GPUs, serving expertise and usually a quality gap at the frontier.

The process: prototype with the strongest model to learn whether the task is feasible and set the quality bar; build the eval set; try cheaper, faster models against it and send only the hard cases to the expensive one; pin model snapshots, re-run evals before every upgrade, and keep a tested fallback.

**Customising behaviour: prompt, RAG, tools or fine-tuning**

```mermaid
flowchart TD
    Q{"What is failing?"} -->|"missing, private or<br/>changing knowledge"| R["RAG<br/>(cite, permission,<br/>re-index to update)"]
    Q -->|"needs live data<br/>or actions"| TL["Tools / APIs"]
    Q -->|"format, tone,<br/>task behaviour"| PR["Better prompt<br/>and examples"]
    PR -->|"still inconsistent, or<br/>prompt too long"| FT["Fine-tune<br/>(SFT, LoRA)"]
    Q -->|"multi-step<br/>reasoning"| RM["Reasoning model,<br/>decomposition"]
    Q -->|"too slow or<br/>too expensive"| SM["Smaller model,<br/>routing, caching"]
    SM -->|"quality drops"| DS["Distil the large<br/>model into a<br/>small one"]
```

- **Prompting** first: cheapest, fastest to iterate.
- **RAG** for knowledge the model lacks or that changes: answers cite sources, respect per-user permissions and update by re-indexing.
- **Tools** for live data and actions: prices, account state, calculations.
- **Fine-tuning** for behaviour: a consistent format or style, a domain-specific task pattern, shorter prompts (the instructions move into the weights), or a small model matching a large one on a narrow task. It is a poor way to add facts: no citations, retraining for every update, facts still hallucinated, no permissions.

**Fine-tuning methods**

- **Full fine-tuning** updates every weight. Best fit, but it needs the most GPU memory (weights, gradients and optimiser state) and risks **catastrophic forgetting** of general skills.
- **LoRA (low-rank adaptation)** freezes the original weights and learns a small update for chosen weight matrices: the update is the product of two thin matrices, B times A, with a small rank r (typically 8 to 64).

```mermaid
flowchart LR
    X["Input x"] --> W["Frozen weight W<br/>(d x d)"]
    X --> A["A: d to r<br/>(trainable)"]
    A --> B["B: r to d<br/>(trainable)"]
    W --> S["Output:<br/>Wx + BAx"]
    B --> S
```

  For one 4,096 x 4,096 matrix, full fine-tuning trains about 16.8 million weights; LoRA with rank 8 trains 2 x 4,096 x 8 = 65,536, about 0.4%. The adapter is megabytes; one base model can serve many adapters (per task or per customer), or an adapter can be merged into W for zero extra latency.
- **QLoRA** loads the frozen base model in 4-bit precision and trains LoRA adapters on top, so large models fine-tune on a single GPU.
- **Data**: hundreds to a few thousand high-quality (input, ideal output) pairs that look like production inputs, including edge cases and refusals. Quality beats quantity; hold out a test set.
- **Preference tuning**: RLHF with a learned reward model and reinforcement learning, or DPO trained directly on chosen-versus-rejected pairs (simpler and more stable; RLHF's reward model is reusable and more flexible).
- **Distillation**: a large **teacher** labels many real inputs; a small **student** is fine-tuned on those outputs and matches the teacher on that narrow task at a fraction of the cost and latency.

"The large model is 95% accurate but too slow and expensive": pin down the target (eval set, latency and cost budgets); take the cheap wins (shorter prompt, prompt caching, batch API for offline work, a smaller model with a better prompt); distil (run the large model on thousands of real inputs, filter its outputs with validation and spot checks, fine-tune a small model with LoRA, compare on the held-out set); cascade (the small model answers first, low-confidence cases go to the large model); then monitor for drift and refresh the training data. Fine-tuning brings its own risks: overfitting, forgetting, memorised sensitive data, retraining whenever the base model is upgraded, and a permanent eval burden.

Say it like this: "RAG changes what the model knows at request time, with citations, permissions and instant updates; fine-tuning changes how it behaves: format, style, task patterns, or a small model matching a big one. I start with prompting, add RAG for knowledge and tools for live data, and fine-tune, usually with LoRA, only when the eval shows a behaviour gap prompting can't close or cost and latency demand a smaller model."
