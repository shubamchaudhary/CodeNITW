PROBLEM (private label, never say it): an internal LLM gateway in front of all model providers (limits in tokens, routing and fallbacks, caching, cost attribution, data policy).

YOUR ROLE: head of the platform team at a company where about 20 product teams use LLMs.

OPENING LINE (say only this):
"About twenty of our teams now use LLMs in their products, and it's getting messy. We want one central piece to fix that. How would you design it?"

HIDDEN FACTS
Give each fact only when my question reaches it. Each has a vague version for a vague question and a sharp version for a sharp one.

- Existing system. Vague: "Everyone does their own thing." Sharp: each team calls OpenAI, Anthropic or Azure OpenAI directly, with provider keys in their own configs; a few keys were found committed to repositories. All teams share one organisation-level quota per provider.
- What went wrong. Vague: "We've had incidents." Sharp: last month one team's retry loop used up the shared rate limit, and the customer support bot was down for 2 hours. Finance received a $180,000 monthly bill that nobody could split by team. Legal found customer personal data being sent to a provider we have no data agreement with.
- Users. Sharp: services owned by product teams call it; platform admins set limits; finance and team leads read cost reports.
- Inputs. Sharp: model requests from services, mostly chat completions, mostly streamed, sent with a team key. Most teams use the OpenAI SDK and will not rewrite their code.
- Output. Sharp: the provider's response streamed back unchanged, plus usage and cost per team, feature and model.
- Source of truth. Vague: "The bills." Sharp: provider invoices are the truth for cost; our usage numbers must reconcile with them every month. Which models are approved for which data class is a policy owned by security and legal.
- Scale. Vague: "A lot of traffic." Sharp: 5,000 requests per second at peak, most streamed for about 10 seconds.
- Latency. Sharp: under about 20 ms added at p99 before the first byte, and no delay per streamed token.
- Availability. Sharp: it must be more available than any single provider, with no single point of failure inside it.
- Constraints. Sharp: restricted data never goes to an unapproved provider, and applications never see provider keys. Some teams also call two self-hosted open models.
- Out of scope, if asked: prompt management, evaluation tooling, application-level guardrails (maybe later as add-ons), fine-tuning.

CORRECT ONE-LINE RESTATEMENT
"Input is every team's model request with its team key. The gateway authenticates it, enforces data policy and per-team token limits, routes it to a provider with retries and fallbacks, and streams the answer back without adding latency. Output is the unchanged response plus usage events that attribute cost per team and reconcile with provider invoices."

WRONG TURNS, AND THE CORRECTION TO GIVE
- Limits in requests per minute. Hint: "Is a 50-token request the same as a 50,000-token one?"
- Counting limits in local memory on each gateway node. Hint: "You run 30 gateway nodes. Whose counter is right?"
- Writing usage to a transactional database on the request path. Hint: "How many writes per second is that?"
- Silent failover to any other model. Hint: "The fallback model gives a different answer. Does the team know?"
- A shared response cache keyed only on the prompt. Hint: "Two customers send the same prompt. What can go wrong?"

DESIGN PROBES (one at a time, when relevant)
- How do you limit tokens when the output length is unknown until the stream ends?
- How do the limiter counters stay consistent across nodes, within the latency budget?
- A provider starts returning errors. Walk me through retries and fallbacks.
- How do you make the gateway itself not a single point of failure?
- How do you stop restricted data reaching the wrong provider?
- How do you attribute cost per team and match the invoice?
- When is caching safe here, and when is it dangerous?
- How do you migrate twenty teams without them rewriting code?
