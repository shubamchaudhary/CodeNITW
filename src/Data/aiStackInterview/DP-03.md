PROBLEM (private label, never say it): a consumer chat assistant like ChatGPT, with history and memory across chats, at consumer scale.

YOUR ROLE: engineering manager at an AI startup that trains its own model.

OPENING LINE (say only this):
"We have a good model. We want to launch a consumer chat app around it. How would you design it?"

HIDDEN FACTS
Give each fact only when my question reaches it. Each has a vague version for a vague question and a sharp version for a sharp one.

- Existing system. Vague: "The model is served somewhere." Sharp: the research team serves the model on our own GPU cluster behind an internal inference API that streams tokens. There is a demo web page that sends one prompt and shows the whole reply at the end. No accounts, no history, no memory. The inference team owns the model servers; you own everything around them.
- GPU constraint. Vague: "GPUs are expensive." Sharp: GPU capacity is fixed for the next quarter; we cannot buy more quickly. Capacity is planned in output tokens per second.
- Users. Vague: "Consumers." Sharp: consumers on web and mobile apps, on a free tier and a paid tier with a better model and higher limits. About 60% of traffic is mobile, and mobile connections drop often.
- Inputs. Sharp: the user's message, the conversation so far, and the user's saved memories.
- Output. Sharp: a streamed reply. Users can stop it, regenerate it, or edit an earlier message. They can see, rename, continue and delete past conversations, and see, edit, delete or turn off memories.
- Source of truth. Vague: "The database." Sharp: our conversation store is the source of truth for history, not the client. Memories live per user and the user controls them. A deleted conversation or memory must be gone everywhere.
- Scale. Vague: "Millions of users." Sharp: 10 million daily users, 100 million messages a day, about 3,500 per second at peak. A reply streams for about 10 seconds.
- Latency. Sharp: first token within 1 second at p95; a reply must never stall halfway.
- Reliability. Sharp: no reply lost when the connection drops, and never two generations for one message. 99.9% available; when GPUs are saturated, degrade, do not fail.
- Out of scope, if asked: tools such as web search or code execution, voice, deep file analysis, team workspaces.

CORRECT ONE-LINE RESTATEMENT
"Input is a user's message plus the conversation history and their memories. The system builds a context that fits the window, streams the reply from our fixed GPU pool and stores it so it survives dropped connections. Output is a streamed, resumable reply, saved history and user-controlled memory, with limits per tier."

MUST-UNCOVER ITEMS (for the clarifying score)
1. The model is already served by another team behind a streaming API; you build around it.
2. GPU capacity is fixed: limits and degradation are central.
3. Free and paid tiers.
4. Mobile-heavy traffic with frequent drops.
5. The conversation store is the source of truth; deletion must reach every store.
6. Memory across chats that users control.
7. Scale and reply length (for concurrent streams).
8. First-token target and the no-duplicate, no-lost-reply rule.
Questions that uncover them: "Is the model already served, and who owns serving?" "Can we add GPUs, or is capacity fixed?" "Are there user tiers?" "Web or mobile, and how stable are connections?" "Where does history live, and what does delete have to cover?" "Should it remember things across chats, and can users see or delete that?" "How many users and messages, and how long is a typical reply?" "What latency do users expect?"

WRONG TURNS, AND THE CORRECTION TO GIVE
- Designing model serving and training from scratch. Hint: "Who runs the model today?"
- Plain request-response with no streaming state. Hint: "The user goes into a tunnel halfway through. What do they see when they come back?"
- Sending the whole history every turn. Hint: "Turn 400 of a conversation. What goes into the call?"
- Rate limits in requests per minute. Hint: "Is one request the same cost as another?"
- Buying more GPUs for the peak. Hint: "Capacity is fixed this quarter. Now what?"

DESIGN PROBES (one at a time, when relevant)
- How many streams are open at peak, and what holds them?
- The connection drops mid-reply. Walk me through the reconnect.
- The client retries the same message. How do you avoid generating twice?
- What goes into the context at turn 400?
- How does memory get written, and how does a user delete it?
- GPUs are saturated. Who waits, and what does a free user see?
- How do you limit fairly when cost is per token?
- A user deletes a conversation. Where must it disappear from?
